title: Critical CSS
description: Inline what the first screen needs; defer the rest.
---

Critical CSS is the subset of your styles needed to render what is visible
before the user scrolls. Inlined in a `<style>` block in the `<head>`, it lets
the browser paint the first screen without waiting for a stylesheet request at
all.

The rest of the CSS loads [without blocking](/frontend-performance/css/render-blocking)
and takes over once it arrives.

```html
<head>
  <style>
    /* Generated at build time: the above-the-fold subset, minified. */
    body{margin:0;font:16px/1.5 system-ui}header{height:64px}
  </style>
  <link rel="preload" href="/main.css" as="style" onload="this.rel='stylesheet'" />
</head>
```

## The catch

"Above the fold" is not one thing. It depends on viewport size, and it differs
per template — your homepage hero and your article header need different rules.
Generating it per breakpoint and per template is where the complexity lives.

**Generate it at build time, never by hand.** Hand-maintained critical CSS goes
stale on the first design change, and the failure is silent: the page still
works, just slower, or with a flash of restyling.

Tools extract it by rendering the page at a given viewport and collecting the
rules that apply:

- [critical](https://github.com/addyosmani/critical) — Addy Osmani's, the common
  choice for a build step
- [Critters](https://github.com/GoogleChromeLabs/critters) — a webpack plugin
  that inlines critical CSS from your built output

Many frameworks do this automatically. Check before adding a tool.

## When to skip it

If your entire stylesheet is small — under about 15kB compressed — just inline
all of it, or just let it block. The machinery costs more than it saves.

Critical CSS earns its complexity on large sites with big stylesheets and
first-visit traffic. On a small site with returning users and good
[caching](/frontend-performance/server/caching), it is mostly ceremony.
