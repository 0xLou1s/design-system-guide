Images are usually the heaviest thing on a page, and format choice is the
biggest single lever.

| Format | Use for | Notes |
| --- | --- | --- |
| **AVIF** | Photographs | Smallest; ~50% under JPEG. Slower to encode |
| **WebP** | Photographs, anything | ~30% under JPEG. Universal support |
| **SVG** | Icons, logos, diagrams | Vector: scales perfectly, often tiny |
| **PNG** | Images needing lossless, screenshots | Large for photos |
| **JPEG** | Fallback for photographs | Universally supported |

**Default to AVIF with a WebP fallback and a JPEG last resort.** `<picture>`
lets the browser take the first one it understands:

```html
<picture>
  <source srcset="/hero.avif" type="image/avif" />
  <source srcset="/hero.webp" type="image/webp" />
  <img src="/hero.jpg" alt="" width="1200" height="600" />
</picture>
```

GIF is obsolete for animation. An MP4 or WebM video of the same clip is
routinely 10× smaller. Use `<video autoplay muted loop playsinline>`.

## Prefer vectors

For anything geometric — icons, logos, illustrations, charts — SVG is usually
both smaller and better. It scales to any size without blurring, can be styled
with CSS, and compresses well as text.

Run it through [SVGO](https://github.com/svg/svgo) first. Editor exports carry
metadata, hidden layers and excessive precision, often doubling the file.

## Avoid base64

Embedding an image as a data URI in CSS or HTML looks like it saves a request.
It costs more than it saves:

- Base64 inflates the data by about 33%.
- It cannot be cached independently — it is re-downloaded with the parent file
  on every change.
- It blocks on the parent resource, and in CSS it delays rendering.

The old rationale was [request cost](/frontend-performance/html/requests) under
HTTP/1.1. That rationale is gone. For a tiny icon, inline SVG (not base64) is
the better version of this idea.

- [Base64 encoding and performance](https://csswizardry.com/2017/02/base64-encoding-and-performance/)
