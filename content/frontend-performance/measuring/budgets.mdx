A budget turns "make it faster" into a question with an answer. Without one,
performance work has no finish line and no way to fail a build.

## Core Web Vitals

These are the metrics Google measures in the field and uses for ranking, which
makes them the practical default. Each has a "good" threshold measured at the
75th percentile of real page loads.

| Metric | Good | What it measures |
| --- | --- | --- |
| Largest Contentful Paint | ≤ 2.5s | When the main content appears |
| Interaction to Next Paint | ≤ 200ms | How fast the page responds to input |
| Cumulative Layout Shift | ≤ 0.1 | How much the layout jumps around |

**LCP** is usually an image or a heading. If it is an image, it is almost always
fixable — see [images](/frontend-performance/images/compression).

**INP** replaced First Input Delay in 2024. It measures every interaction, not
just the first, which makes it much harder to game. Long tasks on the main
thread are the usual cause.

**CLS** is a design bug more often than a performance one. Reserve space for
anything that loads late: [images](/frontend-performance/images/dimensions), ads,
embeds, and [fonts](/frontend-performance/fonts/loading).

## Resource budgets

Vitals tell you whether the page is fast. Resource budgets tell you *before* it
gets slow, which is more useful in a pull request.

| Resource | Budget | Notes |
| --- | --- | --- |
| Total page weight | < 1500kB | Aim for < 500kB; the median is worse than both |
| JavaScript | < 300kB compressed | The most expensive bytes you can ship |
| Web fonts | < 300kB all variants | Two weights of one family is usually plenty |
| Time to First Byte | < 800ms | Server-side; a frontend fix will not help |

These are starting points, not laws. A documentation site and a mapping
application have genuinely different budgets. Pick numbers, write them down, and
enforce them.

## Enforce it in CI

A budget nobody checks is a wish. Most bundlers can fail a build on size, and
Lighthouse CI can fail on metrics.

```json title="budget.json"
[
  {
    "path": "/*",
    "resourceSizes": [
      { "resourceType": "script", "budget": 300 },
      { "resourceType": "font", "budget": 300 },
      { "resourceType": "total", "budget": 1500 }
    ]
  }
]
```

The point is not the exact numbers. It is that a change which blows the budget
shows up as a failed check on the PR that caused it, while the author still
remembers why they added it.
