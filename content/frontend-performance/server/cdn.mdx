---
title: CDN
description: Physics — distance costs milliseconds you cannot optimize away.
---

A request from Sydney to a server in Virginia takes about 200ms round trip at
best, because light is not negotiable. TLS setup needs several round trips
before any content moves. For a user on the other side of the world, that is a
significant fraction of your load time spent on geography.

A CDN puts a copy near the user. The first request populates the edge cache;
everyone nearby after that is served locally.

**Serve all static assets from one.** Images, CSS, JavaScript, fonts — anything
that does not change per request. Most hosting platforms include a CDN by
default; check before adding another.

## Cache what you can at the edge

A CDN that only caches assets leaves the document uncached, and the document is
the request that blocks everything else. If your HTML is static or
near-static, cache it at the edge too —
[`stale-while-revalidate`](/frontend-performance/server/caching) makes this safe for
content that updates periodically.

## Fewer origins, not more

Splitting assets across several CDNs to "parallelize" is
[obsolete advice](/frontend-performance/html/requests). Each additional origin costs
a DNS lookup, TCP handshake and TLS negotiation. Under HTTP/2, one connection
carrying everything beats several carrying a little.

This is also the argument for self-hosting fonts and scripts rather than pulling
them from a public CDN: one fewer origin in the critical path, and no
third-party availability risk. The old "shared cache" benefit no longer exists —
browsers partition their caches per site.

## Warm the connection when you cannot avoid a third party

If a third-party origin is genuinely required on the critical path:

```html
<link rel="preconnect" href="https://cdn.example.com" crossorigin />
```

This performs DNS, TCP and TLS ahead of the actual request. Use it for two or
three origins at most — each one consumes a connection.
