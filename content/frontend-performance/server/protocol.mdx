## HTTPS everywhere

HTTPS is not only for sites handling payments. Modern browsers gate features
behind it — service workers, geolocation, push notifications, the clipboard API,
HTTP/2 itself. An insecure site is a slower site with fewer capabilities.

Certificates are free via [Let's Encrypt](https://letsencrypt.org/), and most
hosts provision and renew them automatically.

The TLS handshake does cost round trips, but HTTP/2 and connection reuse more
than make up for it. HTTPS is faster in practice than HTTP/1.1 without it.

## Never mix protocols

A page served over HTTPS that requests a resource over HTTP produces mixed
content. Browsers block it outright for scripts and stylesheets, and the feature
simply fails.

Always use `https://` in asset URLs, or protocol-relative paths. Add
`upgrade-insecure-requests` to your CSP as a safety net for URLs you missed:

```http
Content-Security-Policy: upgrade-insecure-requests
```

## HTTP/2 and HTTP/3

**HTTP/2** multiplexes many requests over one connection, removing the
head-of-line blocking that shaped so much older advice. Enable it — it is a
server configuration flag, and it invalidates the optimizations described in
[requests](/frontend-performance/html/requests).

**HTTP/3** runs over QUIC instead of TCP, which removes transport-level
head-of-line blocking and establishes connections faster. It helps most on
lossy mobile networks. Most CDNs support it; it is usually a toggle.

Check what you are negotiating in the Network panel's Protocol column — `h2` or
`h3`. If you see `http/1.1`, that is the first thing to fix.

## Do not use server push

HTTP/2 server push was removed from Chrome and is deprecated. It was difficult
to use without wasting bandwidth on resources the browser already had cached.

Use `preload` instead, which the browser can skip when the resource is cached.
