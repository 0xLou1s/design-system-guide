---
title: Cookies
description: Sent on every single request to the origin.
---

Cookies are attached to every matching request — each image, stylesheet, script
and API call. Unlike page weight, which you pay once, cookie weight is paid
repeatedly and in the *request* direction, where bandwidth is usually most
constrained.

Limits worth respecting:

- **4096 bytes per cookie**, which is also the browser's hard limit.
- **Under 20 cookies per domain**, well below the ~180 browsers allow.

A page making 60 requests with 3kB of cookies uploads 180kB of headers for
nothing.

## Keep them small

**Store an identifier, not the data.** A session ID pointing at server-side
state beats serializing a user object into a cookie.

**Never put JSON in a cookie.** It is bulky, needs URL-encoding — which inflates
it further — and the same data belongs in `localStorage` (not sent) or on the
server.

**Scope them properly.** A cookie on `.example.com` goes to every subdomain
including your asset host. Set it on the exact host that needs it, and use
`Path` to narrow it further.

**Set an expiry.** Cookies without one accumulate and never leave.

## Serve assets from a cookieless origin

A separate domain for static assets means requests carry no cookies at all.
This is the one piece of old domain-sharding advice that still holds — but the
benefit is real only if your cookies are large, and it costs an extra
[connection setup](/frontend-performance/server/cdn).

Fix the cookie size first. If they are small, this is not worth the complexity.

## Check what you are sending

The Network panel shows request headers per request. Look at a static asset: if
it carries a long `Cookie` header, that string is going out with every file on
the page.
