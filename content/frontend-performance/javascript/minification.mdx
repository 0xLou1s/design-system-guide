---
title: Minification
description: Rename, strip, and drop what never runs.
---

Minification removes whitespace and comments, shortens local variable names, and
drops unreachable code. On JavaScript the saving is larger than on CSS or HTML —
commonly 30–40% before compression — because identifier names are so repetitive.

Every modern bundler does this in production by default. If you are using Vite,
Next.js, Rollup or webpack in production mode, it is already on. Check before
adding anything.

```js
// vite.config.js — this is the default; shown to make the knob visible.
export default {
  build: {
    minify: "esbuild",
  },
};
```

[terser](https://github.com/terser/terser) and
[esbuild](https://esbuild.github.io/) are the common minifiers. esbuild is much
faster; terser squeezes slightly harder.

## Tree shaking

Related, and more valuable. Tree shaking drops exports nothing imports — but it
only works on ES modules, because CommonJS is too dynamic to analyse statically.

```js
// Whole library may be included.
import _ from "lodash";

// Only what you use, if the package ships ES modules.
import debounce from "lodash-es/debounce";
```

Two things break it: packages that only ship CommonJS, and side effects. If a
module does something at import time, the bundler cannot safely remove it —
that is what `"sideEffects": false` in `package.json` declares.

## Source maps

Ship them, but do not serve them to everyone. Source maps make production errors
debuggable; they also expose your original source.

Upload them to your error tracker and keep them out of the public bundle, or
serve them only to authenticated users. Most error-reporting services have a
build step for exactly this.

## Do not minify by hand

Never commit minified code, never edit a minified file, and keep the original
source in version control. This sounds obvious, but minified vendor files
checked into a repo are common, and they are unmaintainable.
